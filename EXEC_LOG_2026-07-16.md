# Task Execution Log: SVE BFDOT Flash Attention Port

**Date:** 2026-07-16
**Goal:** Replace the flash-attention kernel in `attn_bf16_kernel/` with a fully-vectorized,
SVE-only BFDOT kernel adapted from `kutacc/src/attention/flash_mha/flash_attention.cpp`,
and benchmark 1k/2k/4k prefill at Qwen3-0.6B / 1.7B attention shape.

## Problems to Solve

1. Port kutacc's flash attention (SME/ZA-based) to a standalone SVE **BFDOT** kernel.
2. Fully vectorize: QK^T, online softmax, and P·V all in SVE — no scalar inner loops.
3. Use **only SVE** instructions: no NEON (`arm_neon.h`), no SME (`svmopa`/ZA/`__arm_streaming`).
4. Packing: **do not pack Q/K**; **pack V** to V^T. (Confirmed with user 2026-07-16.)
5. Benchmark 1k / 2k / 4k for Qwen3-0.6B and Qwen3-1.7B.

## Findings (established before implementation)

### F1. kutacc's kernel is SME, not SVE — and that is *why* it packs Q and K
`qk_gemm_4vl_1vl` / `pv_gemm_2vl_2vl_out_gemv` in `gemm.h` are `__arm_new("za") __arm_streaming`
and built on `svmopa_za32_bf16_m` (outer-product accumulate into the ZA tile). MOPA dictates
operand layout, so the kernel pre-packs Q, K **and** V
(`block_pack_bf16_1VL_trans_gemm_varlen`, `block_pack_bf16_2VL_gemm_varlen`).
BFDOT has no ZA-layout constraint, so that packing rationale does not carry over.

### F2. BFDOT decides the packing, and it agrees with the user's instruction
- `QK^T` contracts over `head_dim`, which is contiguous in **both** Q rows and K rows
  → feed `svld1_bf16` directly. **No Q/K pack.**
- `P·V` contracts over **keys**: contiguous in P, but stride-`D` in V
  → V must be transposed to `Vt[d][k]`. **Pack V only.**

Consequence (accepted): without a packed K, BFDOT cannot use the `svbfdot_lane` outer-product
form, so each score/output element ends in one `svaddv` horizontal reduction. Mitigate with
multiple independent accumulators (several j per pass) for ILP. This is the documented
"BFDOT is GEMV-friendly" path.

### F3. *** GCC 13 miscompiles `(bfloat16_t)float` casts — DO NOT USE THEM ***
`aarch64-linux-gnu-gcc 13.3.0`, `-march=armv8.6-a+sve+bf16`:

```c
bfloat16_t a[64];
for (int i = 0; i < 64; i++) a[i] = (bfloat16_t)1.0f;   /* -> bits 0x3c00 */
```
`0x3c00` is **IEEE fp16** 1.0. bfloat16 1.0 is **`0x3f80`**. The compiler applies fp16
conversion semantics to the cast. Reproduces identically at `-O0` and `-O2`, so it is not an
optimizer artifact. It is easy to miss because fp16 and bf16 share the encoding `0x4000`
for 2.0 — a probe using only 2.0 looks correct.

**Rule for this kernel:** never convert float→bf16 with a C cast. Use either
- the explicit `uint16_t` bit-pattern helper (`f32_to_bf16`, round-to-nearest-even), as
  `attn.c`/`flash.c` already do, or
- the SVE intrinsic `svcvt_bf16_x` (verified correct, see F4).

Repro: `scratchpad/probe3.c`.

### F4. The SVE path itself is sound under QEMU 8.2.2 `-cpu max` (VL=512 bits)
Verified against scalar references:
- `svbfdot_f32` on bit-pattern bf16: `64x(1.0*2.0) = 128.0` OK; `sum(1..64) = 2080.0` OK.
- `svcvt_bf16_x` + `svuzp1_bf16` (fp32→bf16, vectorized): matches the scalar RNE reference on
  all 32 lanes, 0 mismatches; round-trip through `svbfdot` exact.

So the vectorized fp32→bf16 softmax→P conversion is viable; only the C cast is broken.
Repro: `scratchpad/probe2.c`, `scratchpad/probe4.c`.

### F5. `fast_exp` is portable as-is
`kutacc/src/math/fast_exp.h` is pure SVE (`svexpa`-based exp2 polynomial), no SME.
Portable to C with only namespace/`auto` removal.

### F6. Qwen3-0.6B and Qwen3-1.7B have IDENTICAL attention shapes
Both: 16 Q heads / 8 KV heads (GQA group=2) / head_dim 128 / 28 layers.
Only `hidden_size` differs (1024 vs 2048), and that never reaches the attention kernel — it
only sizes the QKV projections. Benchmarking both therefore yields identical numbers.
Per user decision (2026-07-16): benchmark the shape **once**, label it as covering both models.

**Goal:** fix two *test-harness* weaknesses found after the kernel was verified. Kernel compute

### Problems to Solve (round 2)

6. The pass tolerance (`atol = rtol = 2e-2`) was ~30x looser than the real bf16 noise, so a
   uniform 1% output error passed all 9 cases.
7. The qwen3 1k/2k/4k check used `ref_cap=8` as a **prefix**; since those cases are causal with

### F10. Real bf16 noise measured: worst `err/scale` = 2.76e-3 across 129 shapes x 2 VLs

Instrumented copy — **saved as `tolerance_probe.c`** (Rule 2; the earlier steps' probes lived in
an ephemeral scratchpad and are now lost, so this one is kept in-tree; it has build/run lines in
its header) — printed `mad/maxref` for a sweep of
D = 1/2/3/7/8/16/33/40/64/65/96/128, Sq/Sk block edges 63/64/65/127/128/129 (all 36 pairs),
`Sk < Sq` causal, GQA g = 1/2/4/16, decode Sq=1 with Sk up to 1024, full-reference multi-block
causal at 256/384/512, causal + non-causal — at **VL=512 and VL=2048**.

| statistic | value |
|-----------|-------|
| n cases | 129 (x2 VLs) |
| median | 1.57e-03 |
| p90 | 2.17e-03 |
| **max** | **2.76e-03** (`D=8`, non-causal) |
| the shipped 9 | <= 1.70e-03 |

VL=512 vs VL=2048 were **numerically identical** except one case in the 3rd digit
(`D=3 full`, head-norm 2.80e-3 vs 2.81e-3). Worst case identical to 4 digits. So the noise is
VL-invariant and the tolerance needs no VL margin.

Why the non-causal cases dominate: the error is bounded by `2^-9 * max_j|V[j][d]|` (bf16 P), so
it is set by `max|V| ~= 1.0` regardless of shape. For **causal**, `maxref ~= 1.0` too (row 0
attends one key, so `O[0] = V[0]` exactly), and `err/scale ~= 2^-9`. For **non-causal**, the
softmax averages ~96 random V's so `maxref` falls to 0.12–0.24 while the error does not — the
denominator shrinks, and `err/scale` rises. Non-causal is the conservative direction.

### F11. Per-ROW and per-HEAD normalisation are degenerate at small D — per-CASE is the robust one

Measured all three on the same data:

| normaliser | worst on a CORRECT kernel | verdict |
|-----------|---------------------------|---------|
| per-row `mad_i / max_d abs(O[i][d])` | **1.159** (`D=1` causal) | **rejected** |
| per-head | 5.60e-03 (`D=1` full) | rejected |
| per-case | 2.76e-03 (`D=8` full) | **chosen** |

At `D=1` a row's scale is a *single* element; when it cancels to ~0 the relative error explodes
on a correct kernel. Per-head fails the same way, more mildly: the offending `D=1` head had
`maxref=0.116` while its absolute error was a perfectly normal 6.5e-4 — the *denominator* was
the anomaly, not the numerator. Pooling the whole case makes the scale estimate robust.

### F12. **The prefix check was blind to a dropped key block — spread rows catch it**

Direct A/B, same data, same tolerance, kernel deliberately broken with
`if (kj == BK) continue;` (silently drop the 2nd key block), qwen3 shape Sq=Sk=512 causal:

| reference rows | err/scale | verdict |
|----------------|-----------|---------|
| prefix 0..7 (OLD) | 1.3e-03 | **PASS** — indistinguishable from a correct kernel |
| spread 0..511 (NEW) | **1.5e-01** | **FAIL** — 19x over the bound |

This is the concrete justification for Problem 7: the old harness would ship a kernel that
silently drops an entire key block. Rows 0–7 never reach block 1, so no tolerance however tight
could have caught it — it was a *coverage* bug, not a tolerance bug.

### F13. `err/scale` is diluted ~7x on causal spread-row checks (known, accepted limit)

For causal `Sq==Sk`, `maxref ~= 1.0` comes from row 0 (`O = V[0]`, zero error), while the error
comes from the late rows whose own scale is only ~0.13. Measured at qwen3 1k with spread rows:
per-case `err/scale = 2.92e-04` but per-row `= 2.20e-03` — a ~7.5x gap. So a *subtle* (~1%)
drift confined to late rows is under-reported by ~7x at the long shapes and would need to reach
~5–6% of the row's own magnitude to trip TOL. **Structural** multi-block bugs are far above that
(F12 measured 1.5e-01) and are caught loudly. Per-row normalisation would close this gap but is
unusable (F11). Accepted and documented; the natural follow-up, if ever needed, is a per-row
bound with a floor tied to the case scale.

### Tolerance chosen: `TOL = 8e-3`, criterion `mad <= TOL * maxref`

Replaces `|k-r| <= atol + rtol*|r|` (atol=rtol=2e-2). The old form mixed an absolute term that
**dominated** — against outputs of O(0.1–1.0) it evaluated to an effective ~3e-2 bound, ~30x the
real ~1e-3 noise. The new criterion is normalised by the per-case output scale, so **the printed
`err/scale` IS the pass metric** — headroom is readable straight off the output line.

Margins: **2.9x** over the global measured worst (2.76e-3), **4.7x** over the shipped suite's
worst (1.70e-3), ~27x over the qwen3 long cases.

**Honest note on the "~4-5x" target:** 4-5x over the *global* worst would be 1.10e-2–1.38e-2,
which is **above 1e-2 and so would NOT catch a clean x1.01** — a uniform scale error `e` lands
`err/scale ~= e` (the max-|ref| element carries the max absolute error). The sensitivity
requirement therefore **caps the usable margin at ~3.5x**; the two requirements are in tension
and 8e-3 is the balance. It is 4.7x over what the suite it actually guards exhibits.

### F14. F9 was live on `odd + multiblock`: 360/780 rows (46%) were never actually compared

**The earlier claim that "every shipped causal case has `Sk >= Sq`" was wrong** (corrected in
place at F9 and at the Residual-limits bullet). `odd + multiblock` is `Sq=130, Sk=70, causal`,
so `lim(i) = i-60 < 0` for rows 0..59 → 60 fully-masked rows/head × `Hq=6` = **360 of 780**
checked rows. `attn_ref` divided by `sum==0` there, giving `0/0 = NaN` across the whole row;
`NaN > tol` is false, so those rows passed **vacuously** — and NaN never updated `mad`/`maxref`
either, so nothing in the printed output hinted at it.

Severity: `odd + multiblock` is the **only** short-suite case spanning >1 query block *and* >1
key block. The one case guarding the multi-block online-softmax path was the one case that was

**Measured, instrumented build (`scratchpad/flash_nan_before.c` / `_after.c`), NaN reference rows:**

| case | before | after |
|------|--------|-------|
| MHA prefill / prefil.causal / GQA ×3 / MQA / decode ×2 / big head_dim | 0 | 0 |

### The two fixes

1. **`attn_ref`: emit a zero row, not NaN, for a fully-masked row.** `s[j] /= sum` →
   `float inv = (sum > 0) ? 1.0f/sum : 0.0f; s[j] *= inv;`. This mirrors the kernel's
   `l==0 -> inv=0` exactly, and matches standard flash-attention. It cannot misfire on a real
   row: with ≥1 valid key the argmax term contributes `expf(0)=1`, so `sum >= 1` strictly.
2. **`run_case`: NaN-safe comparison.** Non-finite elements are counted **out-of-band**
   (`long nbad`) and fail the case unconditionally: `int ok = (nbad == 0) && (mad <= TOL*maxref)`.
   Out-of-band is deliberate — a NaN cannot be carried *in* `mad`, because `!(ad <= mad)` would
   latch NaN and then the **next finite `ad` would overwrite it** (poison, then un-poison). The
   final test keeps the `mad <= bound` form (fails closed on NaN) rather than `!(mad > bound)`.
   The verdict names the count (`*** FAIL (N non-finite) ***`) because `err/scale`, computed from
   the finite remainder, looks perfectly innocent when NaN is the bug — see the A/B below.
